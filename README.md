# MFA Code Fetcher — 邮箱 MFA 验证码 + TOTP 动态口令 自动填充

[English](README.en.md) · 中文

**别再手敲 MFA 验证码了。**

每次连 VPN，邮件来了，你切窗口、抄六个数字、粘进去，还得祈祷窗口没过期。MFA AutoFill 把这个循环干掉——验证码一出现就自动落进正确的输入框，你可以直接回去干活。

它提供两条互相独立的通道，用哪条、或者两条一起用都行：

| 通道 | 工作原理 | 需要 Python 脚本吗 |
|---|---|---|
| **邮箱验证码** | 本地 Python 脚本监听你的 IMAP 邮箱，识别 MFA 邮件、提取验证码，并通过 `127.0.0.1:8642` 提供出来；浏览器扩展轮询这个接口，把验证码填进验证框。 | 需要 |
| **TOTP 动态口令** | 扩展自己实现 RFC 6238。把注册 authenticator 时拿到的 Base32 秘钥存进去，扩展就变成一个装在浏览器里的 authenticator：每次填充都取当前 30 秒的新码。 | 不需要 |

### 为什么这样设计

- **没有预置域名。** 大多数 MFA 页面要么是内网的，要么是特定厂商的，谁也没法预知你会用哪个域名。旧版本把厂商域名硬编码进 manifest，对一个通用工具来说这是错的。现在扩展**只**往你在弹窗里授权的域名注入脚本，而且就在那一刻申请权限——仅此而已。
- **什么都不出本机。** TOTP 用 Web Crypto 在本地计算；邮箱通道只跟你的 IMAP 服务器和 `127.0.0.1` 打交道。没有统计、没有远程日志、没有第三方服务。
- **只处理你自己的账号。** 它读的是你自己邮箱里的码，不破解、不绕过、不重放任何一个验证因子。第二因子仍然得由你本人通过——这里只是省掉手敲那一下。
- **最后一步留给你。** 它填码，但绝不替你点提交。

### 还处理了这些情况

- 分格输入——页面把验证码拆成六个独立小框时（腾讯云、Google 风格），逐格填入，每格都派发键盘事件
- React / Vue 受控输入——通过原生 setter 赋值，让框架真正感知到值
- 没有任何属性和标识的裸输入框——按标签和邻近文案打分定位，包括 open shadow root 里的输入框和 `position:fixed` 浮层
- 以前能填、现在填不了？弹窗会给出实时诊断：是否已注入、是否识别为 MFA 页面、找到几个分格框、走的是哪条通道、本地 API 不可达的真实原因
- 脚本侧按月切分日志，自动清理两个月之前的；另有 `--diag` 模式逐封打印最近邮件的完整判定链——漏收验证码时第一个该跑的命令

## 使用边界

- **只服务于你自己的账号**：读的是你自己邮箱里、发给你的验证码；不破解、不绕过任何二次验证，MFA 该过还是得由你本人过
- **不联网**：TOTP 全本地计算；邮箱通道只连你自己的 IMAP 服务器和 `127.0.0.1` 上的本地 API，没有任何遥测或第三方服务器
- **拿不准就先问 IT**：如果你所在组织对"脚本读取邮箱 / 浏览器自动填充验证码"有安全策略，请先确认再用
- 凭据都在你本机：`config.json` 存专用密码、`chrome.storage.local` 存 TOTP 秘钥，均不上传。**不要**把它们提交到仓库或发给别人

> **v1.3.0 核心变更：域名完全由你的配置驱动，扩展里没有任何预置站点。**
> 旧版把 `*.example.com`、`*.tencent.com` 等厂商域名硬编码进 `manifest.json`。作为开源工具这是错的——别人用什么域名无法预知。现在改为：**你在弹窗里给哪条记录/哪个站点配了域名，扩展就只往哪些域名注入脚本**，其余站点一律不注入、不申请权限。

## 一次性配置（约 3 分钟）

1. **生成飞书专用密码**（只能在飞书桌面客户端操作，网页版/手机端不行）：
   飞书客户端 → 左上角头像 → 设置 → 邮箱 → 第三方邮箱客户端登录 → 进入设置 → 选 Mac → 生成
   （如果找不到该选项，说明公司管理员未开启，需要找 IT 开通）
2. 复制本目录：`cp config.example.json config.json`
3. 编辑 `config.json`，填入你的邮箱地址和刚生成的专用密码

## 使用

```bash
# 先验证配置（登录一次就退出）
python3 mfa_code_fetcher.py --test

# 常驻监听：收到 MFA 邮件时自动复制验证码 + 弹通知 + 启动本地 API
python3 mfa_code_fetcher.py
```

推荐连 VPN 前就把脚本挂着。收到验证码后 macOS 右上角会弹通知并伴有提示音，验证码已在剪贴板，去浏览器页面直接 `Cmd+V` 粘贴。

## 自动填充（方案二：Chrome 扩展）

脚本运行时会自动在 `127.0.0.1:8642` 起一个本地 API（`/code` 返回 5 分钟内的最新验证码）。
安装扩展后即可自动填入：

1. Chrome 打开 `chrome://extensions`，右上角开启「开发者模式」
2. 点「加载已解压的扩展程序」，选择本目录下的 `extension/` 文件夹
3. 保持 `mfa_code_fetcher.py` 在后台运行，正常连 VPN 即可

**扩展行为**：
- 脚本只注入到你**已授权的域名**（见下一节）。注入后若页面出现 "MFA / Email Code / verification code / 验证码 / 二次验证 / 安全码 / 登录保护 / authenticator" 等字样，右上角会出现紫色状态条「MFA AutoFill 已激活」
- 域名已授权但**没配置任何通道**（既没 TOTP 记录匹配、也没启用邮箱验证码）时，状态条会显示「本页未启用自动填充 — 点扩展图标可启用」，这是提示而非故障
- 每 3 秒取一次码（最长等 5 分钟），取到后自动填入（React / Vue 兼容），状态条变绿色显示验证码
- **支持分格验证码输入**：页面把验证码拆成 6 个单字符输入框时（如腾讯云、Google 风格），会逐格填入并逐框触发键盘事件
- 同一个码填过一次不会重复填；确认按钮**不会自动点击**，最后一步由你掌控
- 点击扩展图标可打开工具栏弹窗：查看最新验证码 / 一键复制 / 检查本地服务状态 / 「强制填充当前页面」按钮
- 弹窗顶部有**本页启用状态条**（黄色=未启用，带「启用本页」按钮；绿色=已启用），底部会**实时探测**当前页面：显示是否已注入、是否识别为 MFA 页面、分格框数量

## 让某个站点自动填充（v1.3.0 的授权模型）

扩展安装后**默认不往任何网站注入脚本**。启用某个站点有两种方式，都在弹窗里完成：

**方式 A：这个站点用 TOTP 动态口令**
「+ 添加秘钥」→ 填名称 / Base32 秘钥 / 绑定域名（可点「用当前页」自动填）→ 保存。保存瞬间会弹出 Chrome 权限对话框（"读取和更改 xxx 上的数据"），点允许即可。

**方式 B：这个站点用邮箱验证码**
打开该站点的登录/验证页 → 点扩展图标 → 弹窗顶部黄色条显示「本页 (xxx.com) 未启用自动填充」→ 点「启用本页」→ 在权限对话框点允许。

授权完成后：弹窗顶部变绿色「本页已启用」，并且**会立刻把脚本注入当前标签页**，不用手动刷新（v1.3.1 起）。其它已打开的同类页面仍需刷新一次。

> 两种方式都指向同一份权限：`https://*.你填的域名/*` 与 `http://*.你填的域名/*`（同时申请 http，因为内网 MFA 页面常跑在 http 上；Chrome 里是一次对话框）。已授权但想收回，去 `chrome://extensions` → 本扩展「详情」→「网站访问权限」里移除即可；撤销后扩展会立刻注销对应注入。
>
> 弹窗里每条 TOTP 记录下方会显示授权状态：已授权只显示域名，未授权会多一行「未授权自动注入 [授权]」。

**为什么需要这一步**：MV3 的 `optional_host_permissions` 要求用户逐个域名确认。这是安全代价，也是取代预置域名清单的正解——扩展不需要事先知道你会用哪些网站。

**「站点访问权限」里的那些开关，要手动开吗？** 不用，插件也没有 API 能替你打开它们。因此 v1.3.4 起做了三层兜底，让这个不可靠的开关**不再阻塞使用**：

1. **打开弹窗即注入**：只要当前页配置过通道（TOTP 记录或邮箱验证码站点），弹窗打开的瞬间就走 `activeTab` 注入一次 —— 这条路**不受任何开关影响**（弹窗打开本身就是一次用户手势授权）。日常使用可以完全无视那排开关
2. **「立即注入本页」按钮**：状态行检测到"规则已注册但页面未注入"时，会多出一排按钮，点「立即注入本页」立刻生效
3. **「打开权限设置」按钮**：一键直达本扩展的详情页（Chrome/Edge 各自的地址），想改长期行为时不用自己找

> 结论：想让某个站点**长期自动**填充，用弹窗里的「授权 / 启用本页」即可；如果浏览器详情页里的开关显示没打开，那只是显示与动态授权不同步，**以弹窗底部的状态行为准**（显示"已注入 · 识别为 MFA 页面"就是通的）。

- 插件内点「授权 / 启用本页」时浏览器弹出的确认框，和扩展详情里那张开关列表，是**同一份权限的两个入口**，前者授权后就等于后者打开
- 反过来，手动去开关列表里点，并不会让插件知道这个域名该走哪条通道（TOTP 还是邮箱），插件仍然要有自己的记录——所以**授权入口统一放在插件弹窗里**，而不是让你去扩展详情
- Edge / Chrome 对"动态授予的 optional 权限"在扩展详情里的显示偶尔不一致（总开关开着、逐站点开关却显示关闭）。**以运行时为准**：弹窗底部显示「已注入 · 识别为 MFA 页面」就是通的
- 真正能把权限收回去的地方，是扩展详情的站点访问列表或插件自己不再配置该域名；撤销后插件会立即注销对应注入

**扩展详情里「站点访问权限」列出的域名是哪来的？** 只有三个来源，没有任何"藏起来的预置名单"：

| 列表里看到的 | 来源 |
|---|---|
| `http://127.0.0.1:8642/*`、`http://localhost:8642/*` | `manifest.json` 的 `host_permissions` —— 扩展要读本地 API 取邮箱验证码，必须声明，这是固定的 |
| `https://*.你填的域名/*`、`http://*.你填的域名/*` | **你自己点「授权」时申请的**（http/https 成对申请，Chrome 只弹一次框） |
| 旧版本残留的厂商域名 | 从 v1.2.x 升级上来的痕迹。v1.2.x 把这 7 个域名写死在 manifest 里，Chrome 对"曾经授予过"的权限不一定在重载时立刻清掉。它不会让扩展做任何事（代码已不再引用），可以单独关掉，或卸载扩展重新加载一次就干净了 |

**手动兜底**：任何页面都可以点弹窗里的「强制填充当前页」临时注入一次（`activeTab` 权限，点击即授权，不落盘），用来验证页面是否被正确识别。

## 常见问题

- **装完扩展要重启浏览器吗？** 不用。但装扩展**之前**已打开的页面不会自动注入脚本，要刷新一次；以后修改扩展文件后，要在 `chrome://extensions` 扩展卡片上点刷新图标。
- **页面没有任何状态条出现** = content script 没注入，依次检查：
  1. MFA 页面是不是在 **Chrome** 里打开的？（VPN 客户端拉起的是系统默认浏览器——如果是 Safari/Edge，扩展不会运行；可把 Chrome 设为默认浏览器）
  2. MFA 页面地址栏的**实际域名**是什么？如果这个域名没在弹窗里启用过，扩展不会注入——按上一节「让某个站点自动填充」点一次「启用本页」，或临时用弹窗里的「强制填充当前页面」按钮
  3. 状态条出现但显示「本地 API 不可达」：v1.3.5 起它会**逐个地址列出真实原因**，先看是哪一种
     - 文案里有 `[未授权]` / 「站点访问权限已被关闭」→ **这是新版浏览器的坑，不是服务问题**。Chrome/Edge 142+ 允许用户把 `127.0.0.1` 的站点访问也单独关掉；一旦扩展失去这个 host permission，`fetch` 本地服务会直接抛 `TypeError: Failed to fetch`（Chrome 官方 LNA 文档原话：扩展只有在**持有对应 host permission** 时才被豁免本地网络限制）。**点弹窗里红色的「恢复本地 API 权限」一次即可**，或去扩展详情页把 `http://127.0.0.1:8642/*`、`http://localhost:8642/*` 两个开关打开
     - 文案里写「请确认 mfa_code_fetcher.py 正在运行」→ 才是服务侧问题：旧进程（17:31 前启动的）没有 API，Ctrl+C 重启；`curl --noproxy '*' http://127.0.0.1:8642/health` 应返回 `{"ok": true}`
     - v1.3.5 已**移除 `[::1]` 回退**：服务端只监听 IPv4 的 `127.0.0.1`，这个地址永远连不上，之前只会把排查引向「是不是没开 IPv6」这种错误方向
     - 端口冲突就改 `config.json` 的 `api_port`（同时改 `extension/background.js` 和 `manifest.json` 里的 8642）
- **状态条显示「未找到验证码输入框」**：把 MFA 页面输入框的 HTML 结构（右键检查元素复制给我），我来精调 `content.js` 的识别规则
- **填错了输入框**：同上，发 HTML 结构来精调
- **已授权、弹窗也不再提示「未授权」，但页面就是没填充**（v1.3.1 排障）：弹窗底部那行状态会直接告诉你是哪种情况
  - `(规则已注册但页面未注入)` → 绝大多数是 Chrome 把该站点的**站点访问权限**限制成了「点击时」。此时点「强制填充当前页」能立刻生效（走 `activeTab`），但要长期自动，得去扩展详情把该站点开关打开
  - `(该域名未授权注入)` → 还没授权，点「启用本页」
  - `(已注入, 但页面未识别为 MFA 页面)` → 页面正文没有验证码字样，或输入框在**封闭的跨域 iframe** 里（v1.3.1 已支持 `allFrames`，但完全封闭的 iframe 仍可能取不到）
  - `(已注入 · 识别为 MFA 页面 · 分格 N 框)` → 注入和识别都正常，问题在取码环节，看上面「本地 API」那几条
- **域名到底匹配不匹配，别靠猜**：`https://*.cloud.tencent.com/*` 这种写法**同时匹配 `cloud.tencent.com` 本身和它的子域**（Chrome 解析时剥掉 `*.` 前缀后先做精确相等比较，见 Chromium `url_pattern.cc` 的 `MatchesHost()`；MDN 的示例表里也把 `https://mozilla.org/` 列为 `*://*.mozilla.org/*` 的匹配项）。所以配置 `cloud.tencent.com`、页面在 `cloud.tencent.com`，域名这一环是通的，不要再往这个方向查


## 动态口令 (TOTP) — 纯插件实现, 不依赖 Python 脚本

点击扩展图标 → 「动态口令 (TOTP)」区 → 「+ 添加秘钥」：

- **名称**：如 `公司 IDaaS`
- **Base32 秘钥**：绑定时给的秘钥（空格/连字符自动忽略）
- **绑定域名**（可选）：填了它，打开该域名的 MFA 页面时**自动实时算码并填充**（每次填充都取当前 30 秒窗口的码，不存在过期问题；同一窗口不会重复填）；留空则只做"浏览器版 authenticator"，点弹窗里的复制按钮手动粘贴
- **「用当前页」按钮**：一键填入当前标签页的域名，避免手输错误

**记录可编辑**（v1.2.2+）：每条记录右侧有「复制 / 编辑 / 删除」。点「编辑」可修改名称、秘钥、域名，改完保存后**刷新 MFA 页面即生效，无需重载扩展**。

**域名输入容错**：`https://idaas.example.com/`、`IDAAS.Example.com`、`idaas.example.com:443`、带路径的 URL 都会被自动规范化为 `idaas.example.com`；填父域名（如 `example.com`）可覆盖其所有子域名，但 `vpn.example.com` 不会误匹配 `idaas.example.com`。

> 若页面需要动态口令但无记录匹配当前域名，页面右上角会提示「已绑定: xxx — 点扩展图标可编辑域名」，方便快速定位配置错误。

**IDaaS 的「手机软件二次认证」页（如 `vpn.example.com`）走哪条通道？** 看页面上选的 MFA 方式：

- 页面文案是「手机软件二次认证 / Authenticator」→ **TOTP 通道**。给一条 TOTP 记录绑定 `example.com`（填父域即可覆盖 `vpn.*` / `idaas.*` 全部子域）并授权
- 页面选的是「邮箱验证码」方式 → **邮箱通道**（启用本页 + 本地脚本在跑 + 收到新邮件）。注意：TOTP 页不发邮件，邮箱通道在这类页面永远等不到码，这不是故障
- 弹窗底部的「通道: …」一行会显示当前判定结果，例如「页面要求动态口令, 但无 TOTP 记录匹配 vpn.example.com」

**单输入框页面的识别增强**（v1.3.3）：IDaaS 这类"label 写着「输入手机软件中的验证码」、input 本身无任何标识"的页面，现在按输入框**邻近文案**打分定位；同时支持 open Shadow DOM 里的输入框、`inputmode="numeric"` / `autocomplete="one-time-code"` 语义输入框，并改用真实可见性判断（`position:fixed` 弹层不再被误杀）。

TOTP 实现已通过 RFC 6238 附录 B 全部标准测试向量验证，与 Google Authenticator / 飞书验证码等 App 算法完全一致。你原来 Python 脚本算出的码可以直接和插件弹窗里的码比对验证一致性。

**安全提示**：秘钥以明文存在扩展的 `chrome.storage.local` 里（和手机 authenticator 存私钥一个道理），设备别离身。若绑定的是公司账号，建议确认公司安全策略是否允许。扩展只在本机计算、不联网、不上传任何秘钥；但它属于本机的持久化数据，磁盘未加密时会被本地进程读到。

## 提取规则（v1.3.0：双路命中）

判定三级串联，任一级不通过就跳过（并记入日志）：

1. **时效**：只处理最近 10 分钟内收到的邮件（`code_ttl_minutes` 可调），旧邮件直接跳过
2. **特征命中（双路，满足其一即可）**：
   - **发件人白名单**：默认 `notice.aliyun.com`（阿里云通知邮件）——**邮件标题不管怎么变都能命中**，这条是主力
   - **关键词**：默认 `MFA` / `verification`，主题或正文命中即算（`subject_keywords` 可调）
3. **提取验证码**：优先匹配 "code / 验证码 / 校验码 / 动态码" 附近的 4-8 位数字，其次退化匹配 6 位数字

> **为什么加发件人白名单**：阿里云 MFA 邮件标题会随语言模板变化（英文 `MFA verification` ↔ 中文 `二次认证`），只靠关键词会在标题本地化时漏收。白名单按发件人判定，对标题变化免疫。
> 新增发件人来源时，把其域名加进 `config.json` 的 `sender_allowlist` 即可。

## 日志与诊断

- **日志按月切分**：`logs/mfa-fetcher-2026-11.log`、`logs/mfa-fetcher-2026-12.log`……跨月时自动切换（运行中也会切，不必重启）。实时跟踪：`tail -f logs/mfa-fetcher-$(date +%Y-%m).log`
- **自动清理**：保留**当月 + 往前 2 个月**（共 3 个文件），更早的在启动时和每次切月时自动删除。想改保留时长，在 `config.json` 加 `"log_keep_months": 2`（默认 2；写 `0` 表示只留当月，写 `6` 表示留半年）
- **旧版单文件自动迁移**：从旧版本升级上来时，已有的 `logs/mfa-fetcher.log` 会在首次启动时并入当月文件，内容不丢，随后删除旧文件
- **记录内容**：连接、心跳、每封邮件的判定原因、提取结果与异常堆栈
- **诊断模式**：`python3 mfa_code_fetcher.py --diag` — 逐封打印最近邮件的完整判定链（发件人/主题/时间/白名单命中/关键词命中/提取结果/跳过原因），**漏收问题首选这个命令**
- 日志级别：`config.json` 的 `log_level`（`DEBUG` 会额外记录每封被跳过邮件的详情）
- **测试**：`python3 tests/test_log_rotation.py` 可验证切月与清理逻辑（不连邮箱）

## 常见问题

- **邮件收到了但插件没取到码**：跑 `python3 mfa_code_fetcher.py --diag`，看每封邮件的判定原因；若显示"未命中发件人白名单/关键词"，把该邮件发件人域名加进 `config.json` 的 `sender_allowlist`
- **扩展取不到码**：确认脚本在跑、`curl --noproxy '*' http://127.0.0.1:8642/health` 返回 ok；若端口冲突改 `config.json` 的 `api_port`（同时改 `extension/background.js` 和 `manifest.json` 里的 8642）
- **填错输入框**：把 MFA 页面输入框的 HTML 结构（右键检查元素复制给我），我来精调 `content.js` 的识别规则
